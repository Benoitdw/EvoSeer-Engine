EvoSeer is built around a strict layered architecture where each layer has a single responsibility and depends only on layers below it.

```
┌─────────────────────────────────────────────────┐
│  Layer 1 — Data / State                         │
│  Cell, CellState, PluginState                   │
├─────────────────────────────────────────────────┤
│  Layer 2 — Feature Plugins                      │
│  FeaturePlugin ABC + concrete implementations   │
├─────────────────────────────────────────────────┤
│  Layer 3 — Rate Functions                       │
│  RateFunction ABC (translates scores → rates)   │
├─────────────────────────────────────────────────┤
│  Layer 4 — Services                             │
│  MutationStore, MutationGenerator               │
├─────────────────────────────────────────────────┤
│  Layer 5 — Engine                               │
│  GillespieEngine (biology-agnostic event loop)  │
├─────────────────────────────────────────────────┤
│  Layer 6 — Recording                            │
│  Recorder (events, snapshots, final state)      │
└─────────────────────────────────────────────────┘
```

## Key design decisions

**Biology-agnostic engine** — `GillespieEngine` knows nothing about mutations, pathways, or cell biology. It only calls `get_rate()` and `apply_event()`. All biological logic lives in plugins.

**`_dirty` flag on PluginState** — a plugin's score is only recomputed when a mutation lands in one of its `involved_pathways`, or after a division event. This avoids redundant computation in large populations.

**Plugin types are orthogonal** — `rate_function` plugins feed scores into birth/death rates. `mutation_rate` plugins produce μ_i (the per-division mutation rate). They are registered and resolved independently.
